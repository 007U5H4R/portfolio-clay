## 2 · Animation architecture

`<ProductThinkingJourney>` (the `.hit-journey` board) contains:
- `<RadialReveal>` wrapping `<HowIThinkCollage/>`
- `<MediaGate min=1025>` wrapping `<AnimatedJourneyPath/>`
- `<ol>`, where each `<li>` holds a `<StageRoll>` wrapping the `Sheet` card

The cards stay server-rendered. The only client code is the board root (≈ 3 kB of
IntersectionObserver and `setTimeout`) and the path. The runner never re-renders React; it flips
data attributes, and the CSS keys off them:
- On the board: `data-journey-state` (`idle`, `backgroundReveal`, `pathToProblem`, `problemReveal`,
  … `impactReveal`, `complete`, the spec §19 names generated from the stage ids) and
  `data-journey-armed` (the pre-state is in force).
- On each stage: `data-roll`, which goes `rolled` → `rolling` → `settled`.
- On each path segment: `data-draw`, which goes `drawing` → `drawn`.

All motion is CSS keyframes. The durations come from `timeline.ts` as `--jr-radial-ms`,
`--jr-draw-ms` and `--jr-roll-ms` (one source of truth). Only transform, opacity, clip-path and
stroke-dashoffset animate. There is no filter, no layout property, and `will-change` is not used.

`motion/react` was **not** used. Loading it on `/` for what CSS keyframes do natively would cost
most of the remaining budget. First-load JS for `/` is **160.6 kB gz** (budget 180; it was ≈ 159
before this ticket).

## 3 · Total duration

The desktop sequence takes **7.6 s** from the start of the radial reveal to `complete`. Impact
settles at 7.25 s, then the tail and final settle run until 7.60 s. Measured in the browser, it
falls inside the e2e bound of 6.5–8.5 s at 1440. The frame capture read `complete` at 8.0 s.

## 4 · How sequencing works

`buildJourneySteps` is an ordered list of steps with durations that reproduces the spec §6 instants
exactly (unit-tested):

| t (s) | step |
|---|---|
| 0 | radial reveal |
| 0.70 | path → Problem |
| 1.00 | Problem unrolls |
| 1.75 | Problem settles |
| 1.85 | path → Insight |
| 2.10 | Insight unrolls |
| … | … |
| 6.50 | Impact unrolls |
| 7.25 | Impact settles |
| 7.35–7.60 | tail + final settle |

The runner is one `setTimeout` chain. Each step starts only when the previous step's duration has
elapsed, and a card's step comes after the previous card's full roll plus a hold. So card n + 1
cannot start before card n settles. The e2e test checks this from `performance.now()` timestamps
recorded by a MutationObserver; the unit test checks it with fake timers.

A step belonging to a stage also waits until that stage is *eligible*:
- A stage becomes eligible when its box is ≥ 30 % visible, or when it has already been scrolled
  past (IntersectionObserver, `threshold [0, 0.3]`).
- At 1440 all six sit side by side, so the timeline plays straight through.
- In the stacked 2/1-column layouts each card unrolls as the reader reaches it, still strictly in
  order (spec §16).
- The IntersectionObserver watches each stage's parent `<li>`, not the stage itself. Chromium
  measures a target *after* its own clip-path, and a rolled card is clipped to ≈ 28 px, so it would
  never have reached 30 %. This was found and fixed in the first e2e run.

Other behaviour:
- **Runs once per page load.** A module-level flag also stops a client-side return to `/` from
  replaying it.
- **No scroll lock.** Nothing touches scrolling. The e2e test scrolls mid-sequence and checks that
  `overflow` is not hidden or clipped.

## 5 · How path drawing works

`AnimatedJourneyPath` keeps the counted decoration contract (`svg[data-decor="sketch"][data-sketch="journey"]`,
`aria-hidden`, `MediaGate min={1025}` so it is still absent ≤ 1024; EVAL-018 counts are unchanged).
Instead of TKT-99's stretched 1200-unit strip, the geometry is **measured**:
- Each pin sits at the top-centre of its stage box. The positions come from layout offsets, so the
  roll's transform does not skew them, and a ResizeObserver keeps them current.
- `journeyPathSegments` routes a lead-in, five pin-to-pin joins and a short tail (7 segments).
- Every arc rises through the board's top padding and the cards' torn top margins, so it never
  crosses a heading or body text.
- Each end is trimmed to the pin's rim (14 px from its centre), so the line arrives *at* the pin.

The SVG is at z 4, above the cards (z 2) and the collage (z 0), per spec §2. Each visible segment
keeps TKT-99's bold navy 9/8 dashes. It is revealed through its own solid mask path
(`pathLength=1`, `stroke-dasharray 1 1`), whose `stroke-dashoffset` animates 1 → 0 over 450 ms when
the runner sets `data-draw="drawing"`. This way the dash pattern never distorts while the line
draws. A segment starts 250–300 ms before its card unrolls and overlaps the card's first ~200 ms
(spec §3). The tail draws after Impact (spec §20).

## 6 · How the radial reveal works

`RadialReveal` is a positioned `inset: 0` layer around the collage. Its box *is* the board's box
(the e2e test checks the centres to within 1 px).

- **While armed and idle**, it sits at `clip-path: circle(0% at 50% 50%)` with opacity 0.85.
- **Once the runner leaves idle**, it runs `circle(0%) → circle(100%)` over 1.4 s with
  `cubic-bezier(0.22, 1, 0.36, 1)`, and opacity 0.85 → 1. 100 % of the circle's reference radius
  (diagonal / √2) clears all four corners and the collage's bleed.
- **The path starts at 0.70 s**, when this easing has already uncovered most of the area (spec's
  "~65–75 %").
- **At `complete`**, the clip is removed entirely.
- **On boards taller than 1.5 viewports** (stacked tablet/mobile), the origin's y moves to the
  middle of what the reader is looking at when it triggers, because the board's true centre would
  be off-screen. Desktop stays at the exact 50 % 50 %.

The reveal applies to the backdrop (the collage), not the section's paper colour. That surface is
the same paper as the page, and clipping it would also clip the section heading.

## 7 · How the outline was implemented

The outline is TKT-99 round 2's `.hit-paper-ink`: the rim's own torn `clip-path` on a box 1.5 px
larger, in navy at 88 %, behind the rim. It is sharp and follows the torn silhouette. The soft
physical shadow is the existing offset `.hit-paper-shade` layer. There is **no `filter:
drop-shadow`** (EVAL-019).

TKT-110 kept the outline as-is. The roll's clip-path leaves a 24 px margin on the top and sides, so
the outline, the pin and the rotated corners are never clipped mid-roll.

Unverified: the check that the outline reads against every scrap was visual only, at 1440, from the
frame strip.

## 8 · Reduced-motion behaviour

With `prefers-reduced-motion: reduce`, the board is marked `complete` on mount and never armed. The
backdrop is fully shown, every card is settled and unclipped, the path is complete, and there is no
bounce and no roll. Every pre-state rule is also wrapped in `@media (prefers-reduced-motion:
no-preference)`, so CSS alone cannot hide anything under reduced motion.

The same final state applies in these cases:
- SSR and no-JS: the pre-state attributes are never in the HTML.
- The board is not fully below the fold at hydration (for example, a reload mid-page).
- IntersectionObserver is unavailable.

Accessibility (A11Y-1):
- The pre-state hides only with clip-path and opacity, never `visibility` or `display`, so all
  content is always in the accessibility tree and focusable. The a11y-90d test checks the six
  headings are named before scrolling.
- Any focus entering the board before the end skips the whole board to `complete` at once. This is
  tested at 390 and 1440.
- axe is clean on `/` (EVAL-006 and how-i-think EVAL-003), scanned after completion.

## 9 · Compromises

- **Pins sit visually on top of the path, but not by z-index.** A pin lives inside its card's
  stacking context (rotation plus isolation), so it cannot sit above an SVG at z 4 while the card
  sits below it. Instead every segment ends at the pin's rim, so the line never covers a pin.
- **Content stagger order is selector-based.** It uses `.jr-roll > * > :nth-child(n)`, skipping the
  `aria-hidden` pin and paper layers. It follows TKT-99's child order (numeral, h3, tag, principle,
  quote, pill). Adding children before those would shift the stagger, but nothing would break.
- **Parts of the spec were skipped as optional:**
  - the §7 post-landing paper vibration (the card's own recoil happens at the same moment);
  - the §12 path traveller dot;
  - the §20 single pulse of the Impact pin;
  - the §4 "shadow increases" mid-roll step (animating a shadow over clip-pathed torn layers means a
    filter or a box-shadow on a clipped element).
- **`SKETCHES.journey` in `components/paper/sketch-paths.ts` is now unused.** TKT-99 updated it
  moments before this ticket. It was left in place rather than deleted in a file this ticket does
  not own. It is safe to remove in a follow-up.
- **The radial origin moves on tall stacked boards.** It is placed at the viewport middle instead
  of the board's exact centre (see §6). This is deliberate, per spec §16.
- **Coordination with TKT-106 (edge parallax) is untested.** Its CSS was not on this branch. The
  choreography only animates inner elements (the backdrop layer, the stage wrappers, the pins, the
  card children and the mask paths), never the section or the board. A transform TKT-106 puts on
  the section container therefore composes with it and does not conflict. Re-check after
  integration.
