Agree with the Low severity.

**(c) `crawler.ts` timeout→dead classification (EVAL-011 flakiness) — real robustness gap, blocking or note-for-later?**
**Real gap, note-for-later (non-blocking).** Read `tests/e2e/crawler.ts:125–163` (`checkExternal`): a 429/5xx gets a 2 s sleep + one retry before being finalized, but a genuine network **timeout or fetch error** (the `catch` at line 136) is classified `dead` immediately, with no retry and no distinct "inconclusive" verdict — indistinguishable from a real 404/refusal. That is the mechanism behind the documented "may transiently flake on external-link timeout" caveat. In this run the LinkedIn check actually hit a real HTTP 429 (correctly WARN'd as a bot-block, not a timeout), so **no flake occurred this gate** — nothing to rerun. This is a pre-existing crawler-core limitation (M-002/M-004 scope, not introduced by M-005 content), so it does not block this content gate; recommend a follow-up ticket to add a retry-then-WARN path for timeout/fetch-error outcomes the same way 429/5xx already gets one.

**(d) TC-093: featured-3 truth pages need Tushar's human sign-off — confirm evidence exists.**
**Evidence exists; sign-off itself is still pending (as documented, not a defect).** `evals/results/eval-003-bda8555.md` is a complete, real inspection artifact (8/8 rows, method, per-question detail, 6 anchor corrections, 1 logged gap) and `test-cases.md` Appendix D has been updated in place with the "Verified anchor" and "Status" columns.
